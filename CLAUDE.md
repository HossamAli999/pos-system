# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a Laravel 9 multi-tenant POS / inventory / accounting system (an POS-derived codebase). One installation serves many independent `business` tenants (shops), each with its own locations, users, products, and transactions. The core app ships without the paid add-ons — code that depends on them (Superadmin/SaaS billing, WooCommerce, Repair, Essentials/HRM, Manufacturing, etc.) lives under an optional `Modules/` directory (via `nwidart/laravel-modules`) that is **not present** in this checkout; such code paths are guarded at runtime with `Module::has('Superadmin')` etc., so don't assume a module's classes/routes exist.

## Commands

**PHP / backend**
```bash
composer install
cp .env.example .env   # no .env.example is committed — create .env by hand with DB_* and APP_KEY set, then:
php artisan key:generate
php artisan migrate              # or migrate:fresh to rebuild from scratch
php artisan serve --port=8765    # dev server
vendor/bin/phpunit                # full test suite (CI runs this against sqlite)
vendor/bin/phpunit --filter=TestName   # single test
```
There's also a web installer (`public/install`, `resources/views/install/*`) that some deployments use instead of running migrations by hand — check `config/installed` state if a page unexpectedly redirects to `/install`.

**Frontend / assets** — build via Laravel Mix, **not Vite**:
```bash
npm install
npm run dev      # webpack build (development)
npm run watch     # rebuild on change
npm run prod      # production build — run this after any resources/sass or resources/js change
```
`resources/js/app.js` is compiled by Mix, but most page behavior lives in **hand-maintained files directly under `public/js/*.js`** (`pos.js`, `product.js`, `functions.js`, `common.js`, etc.) that are *not* part of the Mix pipeline — they're referenced straight from Blade via `asset('js/xxx.js')` and edited in place.

Asset cache-busting is a static integer (`config('constants.asset_version')`, currently `511`), not a filemtime hash — bump it (or hard-reload with a cache-busting query string) when iterating on CSS/JS locally, since browsers otherwise keep serving the old `vendor.css`/`app.css`/`init.js`.

**Linting**: `.php_cs` (PHP-CS-Fixer, PSR2 + alpha-sorted imports) and `.prettierrc` exist but there's no npm/composer script wired to them — run the tools directly if needed.

## Architecture

**Multi-tenancy is manual, not a global Eloquent scope.** Every query that touches tenant data filters by `business_id` explicitly (typically `session('business.id')` or `auth()->user()->business_id`) inside controllers/Util classes — there is no automatic tenant-scoping trait. When adding a new query, you must add the `business_id` filter yourself.

**Business logic lives in `app/Utils/*` service classes** (`BusinessUtil`, `ProductUtil`, `TransactionUtil`, `ContactUtil`, `CashRegisterUtil`, `TaxUtil`, `ModuleUtil`, `NotificationUtil`, `AccountTransactionUtil`, `RestaurantUtil`, `InstallUtil`), all extending a base `Util`. Controllers pull these in via constructor injection rather than calling Eloquent directly for anything non-trivial — follow that pattern for new business logic instead of putting it inline in a controller.

**Views**: Blade + AdminLTE 2 + Bootstrap 3, jQuery, DataTables (server-side processing), Select2 — no SPA framework in real use despite Vue being installed. Layouts, by purpose:
- `layouts.app` — the authenticated shell (sidebar + header), used by nearly every internal page.
- `layouts.auth2` — split-screen shell shared by login, password reset, and the business-registration wizard.
- `layouts.home` — the public landing page.
- `layouts.guest` — bare shell for public token-based pages (e.g. the customer-facing invoice view).

Two shared Blade components carry most of the UI: `components.widget` (the `.box` card wrapper used on almost every page) and `components.filters` (the collapsible filter panel used on ~35+ list pages). Changing either has app-wide reach.

The sidebar menu is generated by the `nwidart/laravel-menus` package via `Menu::render('admin-sidebar-menu', 'adminltecustom')`, rendered through the custom presenter in `app/Http/AdminlteCustomPresenter.php`. Its markup (`.sidebar-menu`, `li.treeview`, `.treeview-menu`, `data-widget="tree"`) is load-bearing for AdminLTE's own JS (`resources/plugins/AdminLTE/js/AdminLTE-app.js`) — don't restructure it without checking that JS.

**The POS screen** (`resources/views/sale_pos/create.blade.php` and its `sale_pos/partials/*`) is the most JS-fragile page in the app: cart rows are rendered client-side from `sale_pos/partials/product_row.blade.php` as an HTML template, and `public/js/pos.js` binds to dozens of specific element IDs for cart math, discounts, and checkout. Treat structural changes here as high-risk; prefer CSS-only changes and verify with an actual add-to-cart + checkout run, not just a visual check.

**Frontend design-system landmines** (relevant if you touch `resources/sass/`): a custom design layer lives in `resources/sass/_redesign.scss`, imported last from `resources/sass/app.scss` so it loads after `vendor.css` (AdminLTE + Bootstrap + the original theme's `resources/plugins/custom.css`) in `css.blade.php`. Three gotchas worth knowing before changing it further:
- The original theme's `resources/plugins/custom.css` carries **per-skin `!important` rules** (`.skin-blue-light .sidebar-menu > li.active > a { ... !important }`, repeated for ~12 skin classes) at higher specificity than a naive override, even one with `!important` of its own. Prefix competing selectors with `body[class*="skin-"]` to win outright — see the comments already in `_redesign.scss` for the pattern.
- Select2 initializes globally with no explicit width (`__select2($('.select2'))` in `public/js/app.js`), and its own width auto-detection is unreliable on first paint — `_redesign.scss` forces `.select2-container { width: 100% !important; }` with a short list of ID-based exceptions for the handful of selects that are intentionally narrower.
- Use `grid-template-columns: repeat(auto-fit, minmax(Npx, 1fr))` for any card grid under the authenticated layout, not a fixed `repeat(N, 1fr)` — the sidebar eats part of the viewport width, so a fixed column count overflows instead of wrapping at common laptop widths (it will look fine at both a phone width and a wide desktop and still break in between).

**Testing**: real coverage is effectively absent (`tests/Unit/ExampleTest.php` and `tests/Feature/ExampleTest.php` are the scaffold defaults). CI (`.github/workflows/laravel.yml`) runs `vendor/bin/phpunit` against a throwaway sqlite DB on every push/PR to `main`.
